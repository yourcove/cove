# Tag name conflict-resolution specification

This document is the compatibility contract shared by the Cove 1.2 scanner, interactive cleanup service, write-time validation, ordinary tag merge, and the future Cove 1.3 namespace-enforcement migration. A database must never be reported as ready by 1.2 and then interpreted differently by 1.3.

## Namespace normalization

Canonical tag names and aliases occupy one namespace. Cove applies .NET `string.Trim()` and then `ToLowerInvariant()` to derive a namespace key. A canonical name that is empty after trimming normalizes to the literal name `<empty>`. An alias that is empty after trimming is removed. The original casing of a surviving non-empty claim is retained; the namespace key alone is case-insensitive.

The scanner reports a group whenever it finds multiple normalized canonical names, a canonical name matching another tag's alias, one alias key owned by multiple tags, an alias matching its own canonical name, duplicate aliases on one tag, a blank alias, a whitespace-only canonical name, or multiple names that normalize to `<empty>`.

The survivor policy gives canonical claims precedence so an alias alone never forces a needless tag merge. Within the canonical owners, Cove recommends the tag with the most reference-bearing rows in the impact inventory; an alias-only group uses the most-referenced alias owner. The lowest tag ID breaks a reference-count tie, and the interactive tool may select any other owner. Reference scoring includes tagged entities, segments, hierarchy relationships, ratings, other attached rows and documented JSON references, and extension foreign-key references, but not populated scalar fields intrinsic to the tag. A cleanup request rescans impacts inside its transaction and rejects a stale group, claim, recommendation, or survivor that no longer belongs to the reviewed group.

## Simple cleanup

Blank aliases are deleted. Aliases are trimmed, an alias matching its own canonical name is deleted, and duplicate aliases on one tag retain their lowest-ID occurrence. A lone whitespace-only canonical name becomes `<empty>`. When canonical names collide at `<empty>`, the canonical owner with the most references is recommended, the lowest tag ID breaks a tie, and the other canonical claims must be merged or renamed.

Every non-surviving canonical claim can merge its tag into the selected survivor or rename the tag. Every non-surviving alias can merge its owning tag, remove only that alias, or rename the alias. One group may mix these actions across different tags, such as merging one alias owner while removing the same conflicting alias from another owner. Because merge deletes the entire source tag, every claim owned by that source must select merge together; the UI synchronizes those choices and the backend rejects a mixed merge/non-merge plan for one tag. Renames are trimmed and checked against the complete shared namespace in the same serializable transaction. The operation rolls back if a replacement is blank where aliases forbid it, claims another namespace, or leaves the original group unresolved.

## Cross-tag merge contract

Every merge runs in a serializable transaction. An ordinary merge first resolves the requested target and sources under the caller's tag-visibility rules; the administrator-only cleanup service may resolve them through its explicit maintenance bypass. After that boundary, the internal transfer temporarily bypasses row-level read filters so references belonging to other users and content hidden by role rules are not omitted. Set-like relationships are unioned and duplicate rows are removed. Source canonical names and aliases become trimmed survivor aliases unless they are blank, repeat the survivor's canonical name, or duplicate another survivor alias. The survivor retains its own populated scalar metadata; an empty survivor field is filled from the lowest-ID source that has a value. `Favorite` and `Organized` are combined with logical OR.

The service transfers all eight direct tag associations (video, audio, text, performer, image, gallery, studio, and group), tag parent/child relationships, remote IDs, primary and secondary segment references, segment display rules, tag applications including tag-hosted applications, custom-field values and tag-reference custom fields, field provenance, ratings, bookmarks, entity affinities, interactions, playback sessions and intervals, group items, user-session pointers, role entity overrides, role content-rule tag scopes, share links, saved filters, per-user default filters, dynamic-group queries and snapshots, and documented live Cove-owned JSON tag references. Those JSON locations include segment payloads and their displayed field-provenance values, contextual interaction metadata and playback context emitted from tag pages, generic and segment-specific tag criteria in named or per-user default filters, dynamic-group queries and snapshots, role scopes, and share links. Historical scrape snapshots, AI-run records, and opaque extension-defined metadata remain immutable because Cove cannot infer tag-reference semantics from arbitrary JSON.

Hierarchy edges are mapped on both ends, duplicate edges are removed, and self-edges created by the merge are discarded. Ratings and position-addressed custom-field values already present on the survivor win their duplicate key. Mapped tag-application collisions keep the target row while confidence, total occurrence duration, and host duration use the maximum non-null value, preserving threshold-driving data without double-counting possibly overlapping durations. Duplicate scalar field-provenance rows keep a populated target value; a SQL-null or JSON-empty target value is filled from the lowest-ID source row carrying a value together with that value's confidence. Duplicate `aliases` and `remote_ids` provenance arrays are unioned target-first, and their single confidence is retained only when all contributing rows agree. Bookmarks keep the earliest creation time. Affinity counters are summed, boolean affinity state is ORed, and most-recent or greatest-dwell fields retain the corresponding source value. Playback rows with the same user session are combined, their interval union is retained without double-counting overlap, and any persisted watched time not represented by that session's interval rows is preserved as residual history. Conflicting role entity overrides use deny-overrides-allow. Remote IDs are treated as opaque, case-sensitive endpoint/value pairs. Interactions and other append-only history remain separate and are repointed.

Tag artwork participates in the same transaction without weakening Cove's blob-reference safety. The merge holds the global blob-reference lease, validates every newly assigned blob identifier, accumulates detached identifiers across its intermediate saves, and asks the blob service to remove only still-unreferenced payloads after commit. A rollback releases the lease and discards the cleanup plan, while unrelated explicit transactions with blob changes remain rejected.

After each interactive operation the required refreshed scan completes inside the same transaction; only then does the transaction commit, merge events and cache invalidation run, and the API return that snapshot. A failed or cancelled refresh therefore rolls back instead of reporting failure after a committed change. “Apply all recommended” requires the revision of the entire reviewed scan, including each impact-selected survivor, removes conflicting aliases by default, and merges only non-surviving canonical claims, repeating impact scan-and-resolve in one transaction until no groups remain. A reference change that selects a different recommended survivor, a newly introduced or changed group, or a changed claim aborts before cleanup starts, and a safety limit aborts instead of committing a partial non-convergent cleanup.

Before deleting a merge source, Cove queries PostgreSQL's foreign-key catalog for references not covered by the core transfer contract. This includes tables left by disabled extensions. Those counts appear separately in the impact preview, and a merge is blocked while any such source reference remains; the administrator can instead rename the canonical claim, remove or rename an alias, or choose the referenced tag as survivor. An extension-aware transfer contract is still required before Cove can safely move those references. Extension data stored without a foreign key or in opaque JSON is not discoverable by this safeguard and remains an extension responsibility.

The long-term extension contract should let a loaded extension register a tag-merge participant with three operations: preview references for a set of source tags, transfer those references to the survivor inside the caller's transaction, and validate that no source references remain. Catalog discovery remains the fallback and the safety net for disabled or older extensions. A participant must identify every table and JSON shape it owns, define duplicate-resolution semantics, and be idempotent so transaction retries are safe; core must continue to block when catalog references remain after all available participants run.

## Cove 1.3 upgrade guard

Cove 1.3 must begin with a read-only preflight using these exact namespace rules. If any group remains, it must abort before changing data and explain that the administrator must run the latest Cove 1.2.x, open Settings → Operations → Tag Name Conflicts, resolve the reported groups, and retry the upgrade. The error may include group and claim counts but must not include private entity names.

After the preflight passes, the 1.3 migration may perform only deterministic trimming, `<empty>` conversion, and blank/redundant alias removal, then install database enforcement and run a final shared-namespace validation query. It must not make an automatic cross-tag survivor decision. Fresh databases and older databases with no conflicts must not require a 1.2 marker.

## Enforcement work still required for 1.3

The 1.2 checks are software-level compatibility checks, not final schema enforcement. A concurrent writer in another process can pass a read-before-write check, so 1.3 still needs an atomic database design for the cross-table namespace, such as a persisted claims table or equivalent constraint. The database representation must reproduce .NET trimming and invariant case folding exactly or use keys computed by Cove; provider `trim`, collation, regular-expression whitespace, and `lower` functions are not interchangeable with this specification.

All Cove-owned JSON locations listed above are covered, but an extension can store opaque tag identifiers in its own tables or JSON. Extensions that persist tag references need an explicit merge participant before their references can move during an ordinary or cleanup merge. Upgrade tests must cover a fully cleaned database, a partially cleaned database, a database that skipped cleanup, and interrupted or concurrent cleanup.

## Findings from the pre-enforcement branch audit

The earlier `unique-tag-name` work placed destructive normalization in the 1.2 migration set and automatically chose cross-tag survivors. This compatibility release removes that migration; Cove 1.3 must preflight and send unresolved databases back to the latest 1.2.x instead of silently making the data-management decision.

The migration grouped only canonical tag names, then applied blanket alias deletion afterward. It did not model one shared namespace or expose alias conflicts for review: aliases matching any canonical name were deleted, duplicate aliases across all tags kept the lowest alias-row ID rather than the documented tag survivor, and blank aliases were silently removed. The shared scanner and policy now classify name-to-alias, alias-to-alias, self-alias, duplicate-alias, blank, and `<empty>` claims together before any decision is applied.

The migration used PostgreSQL regular-expression whitespace and `lower`, while application writes used .NET trimming and casing. Those operations are not equivalent for all Unicode text or database collations. The corrected specification computes .NET `Trim()` and `ToLowerInvariant()` keys in shared code; Cove 1.3 must persist keys computed by Cove or prove its database representation is byte-for-byte equivalent.

The migration duplicated relationship-transfer SQL instead of sharing ordinary merge behavior. Its coverage omitted or incompletely handled Cove-owned JSON, secondary segment tags, several generic host references, intrinsic tag metadata, cache/event behavior, and extension-owned references. The extracted merge service is now the authoritative core contract and the scanner's impact inventory follows it. A follow-up inventory also found live tag identifiers in tag-page interaction and playback context, segment field-provenance JSON, segment-specific `videoTagsCriterion` and `rawTagsCriterion` filters, and per-user default filters inside UI preferences; the shared finder, impact scanner, and rewriter now cover each of those documented shapes together.

The migration also deleted source canonical names instead of preserving them as survivor aliases. Its share-link rewrite cast every JSON array item to an integer, could abort on malformed legacy values, changed numeric identifiers into JSON strings, and produced nondeterministic array ordering. The shared JSON rewriter now recognizes only documented tag-bearing shapes, preserves numeric versus string representation, deduplicates deterministically, and leaves unknown or malformed content untouched.

Several duplicate policies in the migration were lossy or unsafe. Remote-ID handling exposed an existing inconsistency: the editors deduplicate endpoint/value pairs case-insensitively, while persisted matching is case-sensitive; the migration lowercased them and could discard case-distinct opaque identifiers. Role overrides could retain an allow over a deny and widen access, and target-row preference discarded useful bookmark, affinity, playback, or metadata values. The shared merge contract preserves case-distinct remote IDs, uses deny-overrides-allow, keeps the earliest bookmark time, combines engagement/playback state, and applies deterministic metadata fill rules; Cove should standardize remote-ID casing separately.

Foreign keys owned by extensions can use `RESTRICT`, `SET NULL`, or `CASCADE`, so a core-only merge can fail, orphan meaning, or silently delete extension data. The catalog inspector now previews and blocks those sources even when the extension is disabled; transfer remains blocked until an extension participant exists.

The migration rebuilt the complete tag hierarchy and recomputed denormalized arrays and counts across whole tables whenever any merge existed. Although the hierarchy rewrite retained mapped edges, this made a local name cleanup take broad locks and rewrite unrelated rows. The shared merge service now changes only relationships and derived rows affected by the selected sources and survivor.

The ordinary merge endpoint previously required tag-write permission even though it deletes source tags, and a new dangerous cleanup permission would not automatically reach existing administrators without explicit backfill behavior. Ordinary merge now requires both write and delete, while the cleanup permission is granted to existing Admin roles only and remains hidden from ordinary roles.

An application-level merge running as an Admin could still be subject to per-user and content-rule query filters, omitting other users' ratings, bookmarks, affinities, playback, or associations to hidden entities before deleting a source. The shared merge now uses a transaction-scoped internal filter bypass after endpoint authorization so the transfer contract is independent of the initiating administrator's visibility.

Metadata and import resolvers previously matched canonical names through provider-specific case conversion and could create a tag when the requested text was an existing alias. The shared resolver now gives canonical matches precedence, then aliases, using the same namespace key as the scanner and write validator. When multiple Stash import rows resolve to one namespace owner, the importer also fills empty scalar metadata, ORs favorite state, and unions nonredundant aliases and case-sensitive remote IDs instead of silently discarding the collapsed rows' metadata.

The earlier write hook revalidated every modified tag, so an unrelated metadata edit on a historical conflicting tag could be rejected even though its name had not changed. It also built conflict messages from globally queried persisted claims, which could disclose the spelling of a tag hidden by content rules. The compatibility hook now validates only changed claims and reports the caller's attempted value without naming a hidden owner.

The earlier work had no stale-group revision, serializable cleanup transaction, extension-reference preview, or comprehensive category and transfer fixtures. The compatibility API now rejects a changed claim set, requires a scan-wide revision when applying all recommendations so newly introduced groups cannot be resolved without review, refreshes after every operation, and has focused normalization, scanner, cleanup, merge, authorization, and PostgreSQL catalog tests. Cove 1.3 still needs the full cleaned, partial, skipped, interrupted, and concurrently modified upgrade matrix plus migration-failure recovery UI.

Software read-before-write checks cannot enforce a cross-table namespace against concurrent processes, and SQLite tests cannot validate PostgreSQL collation, regular-expression, constraint, or catalog behavior. Cove 1.2 intentionally supplies compatibility checks and guidance; Cove 1.3 still requires atomic database enforcement, a read-only preflight before any mutation, and a final validation that aborts without exposing private claim names.
